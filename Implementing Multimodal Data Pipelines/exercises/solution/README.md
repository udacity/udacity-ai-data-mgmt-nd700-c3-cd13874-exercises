# Multimodal Apparel Catalog RAG Solution

> A multimodal Retrieval-Augmented Generation (RAG) system for querying apparel catalog PDFs using both text and images.

---

## Overview

This project processes an apparel catalog PDF by extracting text and images, generating vision-based descriptions via an Azure OpenAI model, and enabling natural language querying through a RAG chatbot backed by a Chroma vector database.

**Key capability:** handles multiple images per page, significantly improving retrieval accuracy for catalog-style documents.

---

## Key Features

### Multimodal Data Pipeline

| Modality        | Source                  | Processing             |
|-----------------|-------------------------|------------------------|
| Text            | PDF page text           | Stored directly        |
| Images          | Catalog product photos  | Resized + normalized   |
| Vision metadata | Generated by GPT vision | Structured description |

Text and vision outputs are combined into **multimodal documents** used for retrieval.

---

### Multiple Images per Page

Each image is extracted individually and indexed as its own document, improving retrieval precision:

| Page | Images  | Documents Generated |
|------|---------|---------------------|
| 1    | 4 shoes | 4 documents         |
| 2    | 3 shoes | 3 documents         |
| 3    | 5 shoes | 5 documents         |

---

### 2. Image Processing Pipeline

Each extracted image is preprocessed through the following steps:

1. Convert to **RGB**
2. Resize to **224 × 224**
3. Convert to **NumPy array**
4. Normalize pixel values to **0–1**
5. Store metadata describing the transformation

**Example preprocessing metadata:**

```json
{
  "array_shape_hwc": [224, 224, 3],
  "tensor_shape_chw": [3, 224, 224],
  "normalized_to_0_1": true,
  "dtype": "float32"
}
```

> Preprocessing ensures downstream models receive consistent inputs and documents the transformation pipeline.

---

### 3. Vision Description Generation

Each image is sent to a vision-capable GPT model, which produces a structured description including:

- Main apparel item
- Colors
- Accessories
- Style category
- Likely use case
- Brand or team references
- Natural language summary

**Example output:**

```
Item: Running sneaker
Color: Red with white sole
Style: Athletic running shoe
Use case: Casual running or gym workouts
Summary: Lightweight red running shoe with breathable mesh and foam sole.
```

---

### 4. Multimodal Document Construction

Each document stored in the vector database contains:

```
Page number
Image number
Page text
Vision-generated description
```

**Example document:**

```
Page number: 4
Image number: 2

Page text:
Spring athletic collection.

Image description:
Red running sneaker with breathable mesh and cushioned sole designed for running.
```

**Metadata stored with each document:**

| Field               | Description                        |
|---------------------|------------------------------------|
| `page_number`       | Source PDF page                    |
| `image_number`      | Image index on that page           |
| `image_path`        | Path to the extracted image file   |
| `preprocessing_path`| Path to preprocessing metadata     |
| `has_image`         | Whether an image was extracted     |

---

### 5. Embeddings

Documents are embedded using:

```
text-embedding-3-small
```

These embeddings convert document text into numerical vectors for semantic search.

---

### 6. Vector Database

The system uses **Chroma** as the vector store.

- **Collection:** `apparel_catalog`
- Each stored item represents **one catalog image**

**Advantages:**
- Fine-grained retrieval
- Improved similarity search
- More accurate RAG responses

---

## Retrieval-Augmented Generation (RAG)

When a user asks a question:

1. The question is embedded
2. The vector database retrieves **top-k relevant documents**
3. The retrieved context is passed to the LLM
4. The LLM generates a grounded answer

The prompt instructs the model to:
- Answer only from retrieved context
- Cite page numbers when useful
- Avoid hallucinating information

## Why Index Images Individually?

### Without Image-Level Indexing

```
Page → multiple shoes
```
Retrieval returns a **page description**, forcing the LLM to guess which item is relevant.

### With Image-Level Indexing

```
Image → one product
```
Retrieval returns the **exact item**, improving precision.

This pattern is widely applicable to:
- Product catalogs
- E-commerce search
- Equipment manuals
- Inspection reports

---

## Design Decisions

### Why Tokenization Is Deferred

Images are **not tokenized during ingestion**. Instead, the system stores raw images and preprocessing metadata. This avoids coupling the dataset to a specific model architecture, allowing different models to process images later.

---

## Limitations

This demo simplifies several aspects of production pipelines:

- No image deduplication
- No bounding box detection
- No object segmentation
- No image embedding model (text embeddings only)

> In real systems, dedicated image embedding models may also be used alongside text embeddings.
